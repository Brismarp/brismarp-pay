Relatório de execução

O que o git do Brismar Pay contém desde a primeira commit até a suíte de testes: a plataforma ligou, o console do lojista ficou completo para o sandbox, a API pública por chave entrou nas rotas de cliente e cobrança, e as três camadas de teste (incluindo Playwright do /admin) passaram a rodar no CI.

1. Resumo

O repositório nasceu já com a base escrita: schema Prisma, provider mock, painel Next, painel admin e a maior parte das regras de domínio. A primeira commit (dc1ffe3) só guarda esse ponto de partida. O que este histórico fez foi tornar isso executável e verificável.

A API passou a subir de verdade (módulos Nest, Makefile, migration, health no CI). O lojista passou a editar cliente, gerar API Key, estornar cobrança aprovada no mock e sair de listas vazias com um próximo passo. Integrações passaram a autenticar as mesmas rotas de clientes e cobranças com X-Api-Key. No fim, unitários, HTTP contra Postgres+Redis e Playwright do lojista e do painel /admin fecharam o ciclo — ainda com PAYMENT_PROVIDER=mock. A Getnet continua bloqueada: não há contrato oficial no código e este relatório não inventa um.

O que já existe

  • Onboarding de empresa com CNPJ válido e KYB sem auto-aprovação
  • Clientes (criar, editar, buscar) e cobranças mock (PIX/cartão/débito/boleto)

  • Estorno parcial e remoção de clientes
  • Rate limit por chave e OpenAPI
  • Promoção de admin pela própria interface
  • Escopos ledger:read e webhooks:manage em rota alguma

4. Como autenticar

Painel → JWT + cookie de refresh → Integração → X-Api-Key ou Bearer bpay_*

O console usa access token curto em sessionStorage e refresh HttpOnly em bpay_refresh_token (path /v1/auth). Integrações autenticam as rotas /v1/companies/:companyId/customers e /v1/companies/:companyId/charges com X-Api-Key ou Authorization: Bearer começando em bpay_sandbox_ ou bpay_production_. A chave só opera na empresa em que foi gerada.

Continuam só JWT: onboarding de empresa, CRUD de API Keys, dashboard, ledger, admin e auth. simulate-confirmation com chave só aceita ambiente SANDBOX. SANDBOX versus PRODUCTION é rótulo na chave — nenhum dos dois ativa a Getnet.

6. Bugs que o teste encontrou

A suíte HTTP passou a usar o mesmo ValidationPipe e o mesmo cookie parser da API de produção. Dois defeitos reais apareceram e foram corrigidos neste git.

Sintoma Causa Correção
Login com e-mail e senha válidos respondia 400 twoFactorCode no DTO era opcional no TypeScript, mas o pipe exigia a presença do campo 885766f — @IsOptional() no DTO de login
PIX mock ia para FAILED depois de ficar PENDING BullMQ recusa job id com :; o id era recover:{uuid} 885766f — job id recover-{chargeId}

7. Como rodar

Três alvos no Makefile. Unitários não precisam de Postgres nem Redis. HTTP e2e e Playwright usam o Compose (portas do .env, neste ambiente 5433 e 6380).

Camada Comando O que sobe
Unitários make test Jest da API, Prisma mockado
HTTP e2e make test-e2e Nest + Postgres + Redis; sem TEST_* a suíte é pulada
Playwright make test-ui Chromium no lojista e no /admin; API + Next via webServer

Provider permanece mock. No CI, o job api roda unitários e HTTP e2e; o job web instala Chromium, sobe a API e executa os dois walks.
